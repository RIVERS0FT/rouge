# 10846 部队的 20 步/秒验收（2026-11-15）

本轮目标为 **10846 支部队达到正常的 20 步/秒**。固定步长仍为 0.05 秒；每一步更新整场对局。

在用户当前的 VS Code 内置浏览器中，正式本地 Worker 连同状态发送，在 **30.09 秒内推进 602 步，实测 20.00 步/秒**（原始值 20.00385）。采样从 10927 支部队开始，结束时为 11526 支；加载的原始快照为 10846 支。该窗口完整计算平均 **38.08 ms/步**，P95 为 53.6 ms。长步没有从统计中删除；时钟在后续计算有余量时追赶进度。

[当前内置浏览器的原始逐步计时](performance/2026-11-15-simulation-20-integrated.json)保留每次状态接收的 tick、墙钟时间、部队数、全部单步耗时和源码 SHA-256。这是在当前页面启动的隔离对局 Worker，接收端读取状态元数据，未把回放替换进玩家的场景。

另在 Chrome 157 中运行完整客户端状态解码的一分钟窗口，1200 步 / 60.10 秒为 **19.97 步/秒**，计算平均 39.47 ms，解码平均 4.07 ms。[该窗口原始结果](performance/2026-11-15-simulation-20-clock.json)保留其未通过脚本时钟阈值的标记。当前内置浏览器的上述窗口达到 20；不同浏览器和窗口仍存在小幅调度波动，不能据此保证所有窗口均不低于 20 或所有单步均小于 50 ms。

历史 **2.61 步/秒**来自[第二轮报告](PERFORMANCE-SIMULATION-ROUND2-2026-11-15.md)中相同初始快照的 Node 配对计算。本轮用浏览器的实际 Worker 时钟验收绝对目标；不同运行环境的数字不用于计算严格的配对提速倍数。

玩家当前对局已增长到 **24676 支部队**。最终恢复后，包含实际场景显示的 15 秒监测推进 82 步，约 **5.45 步/秒**；这个更大规模仍未达到 20 步/秒。恢复了原对局进度、运行状态和镜头，并确认继续推进，见[恢复与当前实战记录](performance/2026-11-15-simulation-20-continuity.json)。

## 实现

单位位置、属性、路线索引、战斗和碰撞使用 Float64 列数据，由可重复构建的 WebAssembly 内核处理。保留原先的计算顺序、目标 ID 平局规则、伤害累积顺序、移动/碰撞限制和地形容差。地形、建筑与流场索引在加载时建立，路线点保持不可变并复用。

每步按本帧可能发生的相互作用建立连通分量。接敌、溅射、移动和碰撞候选扫描可能关联的部队进入同一分量；整个分量交给一个 Worker，分量内部保持原单位顺序。当前机器最多使用 8 个物理 Worker。碰撞仍为每步 4 轮，每单位推移、候选和约束预算保留，AI 仍按原来的 80 tick 周期错峰执行。

主 Worker 复用列数据和单位统计，减少 JavaScript 对象与空间索引的重复分配。本地快照将单位标量装入可转移的 Float64Array，只发送新增或替换的路线点；接收端重建独立的 UI 状态，旧快照保持不变。LAN 消息和存档格式保持现有版本。

时钟按 50 ms 的计划时刻安排下一步。计算超过一个间隔时不重入，也不额外等待完整的 50 ms；暂停、重新载入会重置时刻。命令在整步之间顺序执行。状态更新以距上次发送的 tick 数判断，因此奇数 tick 切换到 2 倍速也会持续发送。

## 容量和内存

本机采用较大的流场缓存换取计算余量。该实时窗口主模拟 WASM 内存约 **855 MiB**；每个物理 Worker 的几何和路线预留约 **269 MiB**，另有 JavaScript 和浏览器开销。较少内存或处理器线程的设备会使用更少的 Worker/流场缓存，本结果不构成这些设备的速度保证。

临时列数据、线段查询、不可变几何、64 MiB 路线区和按需增长的流场区使用分开的地址范围。导航增长后，失效的统计视图会在同步回退时重建。单步单位数超过 65536、路线区超限、特殊 ID/顺序或 Worker 不可用时，使用同步计算路径；Worker 的超时、失序回复和销毁会结束挂起请求。回退完成已经准备的这一帧，tick 不会重复增加。

`stepParallel` 的状态由调用方独占，等待期间不接受重入步骤或外部命令。调试工具若直接修改步骤之间的 `Engine.state`，应调用 `invalidatePhysicsCache()`；正式本地 Worker 通过命令队列管理状态。
