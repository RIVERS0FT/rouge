# 游戏性能基线与复测

桌面单机以**同一个运行窗口的实际绘帧数和游戏时钟**共同验收。主线程收到 `requestAnimationFrame`、GPU 提交了一帧、Worker 完成一个 tick，是三个独立事件。计时器分别记录三者。保存截图和一秒一条的状态样本，以便核对测量时画面里的兵力和视角。

**本次实测停止于第一轮结束。** 26 个场景已完成 52 个窗口，基础计划共 152 个，整体验收未通过。前 25 个场景在约 32 Hz 的会话中完成首轮配对。优化版 30 分钟长局在第 28 分钟附近出现刷新条件变化，开始和结束时的空白页分别为 32.0 Hz、137.8 Hz。冻结版长局前后均约 32 Hz。长局的整窗帧率不作同条件对比；两边均成功自动保存 20 次，手动档均恢复到写入 tick，13 个旧 Worker 均已关闭，恢复后可正常派遣。高刷新率下的三轮验收尚未完成。

| 更大规模与倍速 | v28 地图合成后期档，每秒核对兵力；真实万兵存档另测 2×，均覆盖 2D/3D | 约 2.5 万单位要求正式窗口内每个采样点在 23,750–26,250 之间（±5%）；2× 对照 40 tick/s |
| 长局与存档 | 30 分钟活动单机，在两个视角间切换，中途手动保存，记录自动保存并重载手动档 | 记录逐分钟 FPS、tick/s、主线程堆大小、存取耗时，核对战役和 tick、重载前的 Worker 已关闭、读档后能实际派遣 |

主场景每个版本跑三个独立窗口，每窗预热 60 秒再测 60 秒。帧间隔 P95 的上限为 33 ms（60 FPS 场景）或 67 ms（30 FPS 场景），最长间隔均为 200 ms。用精确墙钟核对游戏步数，允许客户端每两步发布带来的 2 tick 量化误差。密集战区至少 90% 的采样点需有 180 个以上可见单位；2D 视角全程检查模型数和移动插值轨迹数均为零。

编队压力样本复制真实存档中的位置和指令。两种编队规模的单位按 ID 对应，起始坐标、兵种、归属和各自的目的地相同。行军样本有 219 个不同的编队中心，窄路汇流有 330 个，登陆有 57 个。多军交战把三个国家的 10,000 个单位集中到 5 个原始交战中心，用来观察极端堆叠下的碰撞预算。实战密度取自单独的真实后期存档。

编队移动先按陆地或海面查询邻近编队的占地，复核阻塞和通行条件。地面个体分离则按兵种使用半径 0.46–0.62 的圆，每步做四遍求解；每遍重建空间网格，每个个体只搜索周围九格，最多检查 96 个候选。一个个体每步最多接受 12 次约束尝试，推移距离预算为 0.6。报告中的接触数包含多遍求解中再次遇到的接触；最大穿透表示求解中观察到的峰值。压力表单列触及候选上限、耗尽约束预算的次数，以及有多少 tick 出现这些情况。

首次 1,200 步对照中，330 支编队集中交战时，每步平均检查 50.35 万个候选，406 步触及搜索上限，每一步都有单位耗尽约束预算。两侧的这些计数一致，模拟由 7.68 提升到 10.64 tick/s。1,600 支编队集中交战时，模拟由 6.99 提升到 9.39 tick/s。另一个 1,600 支编队的窄路场景始终有 1,182 个可见模型，模拟接近 20 tick/s，画面由 8.51 提升到 21.14 FPS。

A/B 首轮先跑冻结版，次轮反转版本和场景顺序。比较项按版本取中位数，FPS 和 tick/s 越高越好，P95 帧间隔和反馈耗时越低越好。有指标回退超过 10% 的扩展场景追加三对测量，合并后仍回退则整套不通过。每个窗口记录 GPU、实际渲染像素比以及空白页运行前后的刷新频率。60 FPS 目标使用相同门槛，即便桌面输出刷新率更低。

第 13,878 步的存档另在 Intel UHD 630、1440 × 960 的独立 Chromium 中做了一轮平移对照。2D 的实际绘帧由 31.40 变为 31.49 FPS，同窗模拟由 17.61 变为 14.33 步/秒。近景 3D 由 29.89 变为 32.00 FPS，同窗模拟由 17.27 变为 13.67 步/秒。两个版本在窗口内推进的步数和画面密度有差异，3D 窗口结束时分别可见 373、324 个单位。旧版阻塞解除以后，这一存档的模拟仍有性能开销。

## 复现

本次冻结的是开始优化时的工作区，包含当时已有的未提交改动。实测机器使用 i7-10700（16 个逻辑处理器）、32 GB 内存和 Intel UHD 630，Chromium 153 通过 D3D11 绘制，桌面视口 1510 × 1090、DPR 1.25。起始远程桌面输出 32 Hz。优化版长局结束后，Windows 报告了 144 Hz 的 GameViewer 虚拟显示器和 59 Hz 的 Intel 显示输出。

集成生产构建的完整矩阵有 26 个场景，逐窗记录两侧构建哈希、原始文件哈希、画面密度、帧间隔和模拟步频。未完成的窗口保留待测状态，全部门槛满足后才会将 `accepted` 置为 `true`。[逐轮对照表](performance/2026-11-19-integrated.md) · [集成构建原始指标](performance/2026-11-19-integrated.json)

| 第一版优化，同一真实存档，每项一对 | 优化前 | 优化后 |
|---|---:|---:|
| 2D 实际绘制 FPS | 24.22 | 31.77 |
| 2D 帧间隔 P95 / 最大值（ms） | 93.9 / 250.0 | 31.6 / 250.2 |
| 2D 同窗 tick/s | 14.93 | 16.06 |
| 密集 3D 实际绘制 FPS | 10.04 | 31.72 |
| 密集 3D 帧间隔 P95 / 最大值（ms） | 125.4 / 250.3 | 31.6 / 219.1 |
| 密集 3D 同窗 tick/s | 15.58 | 15.40 |
| 固定 1,200 步，隔离 Worker 的 tick/s | 18.42 | 19.76 |
| 固定 1,200 步，2D 的 tick/s | 16.66 | 18.70 |

这次 3D 窗口每个采样点有 192–217 个可见单位。单独关闭箭头绘制的诊断将瓶颈定位到镜头移动时重复栅格化并上传路线纹理。优化后，已提交路线采用世界坐标三角形，复用原轮廓，在 GPU 上按既有次序绘制箭身和描边。正常渲染保留箭头。编队移动会复核上次阻塞者的当前位置和占地，物理 Worker 复用返回的传输缓冲区。后续版本又减少了阻塞行军的重复计算和本地 Worker 发往 UI 的未变编队记录。

冻结版同步引擎的一次 CPU 采样共 4,234 个样本。其中 42.6% 的调用栈经过编队移动，32.0% 经过步末结算，7.7% 经过地面碰撞分离。碰撞分离属于步末结算，这两个占比有重叠。该结果用于选择优化位置；浏览器内并行工作线程的耗时见固定步数对照。

同步引擎从 tick 20,638 连续推进 1,205 步，每一步的完整状态与碰撞报告都与冻结版同步引擎相同。上表测得的是第一版优化。一轮固定步数 3D 候选测试与回归任务发生重叠，因此该窗口只保留原始数据；汇总文件标记了这一点。各窗口的构建与存档哈希、原始指标见[测量记录](performance/2026-11-19-baseline.json)。

第二版加入编队快照增量传输。真实后期局 2D 的消息到达均值从 9.7 降至 4.7 ms，编码从 5.7 增至 7.6 ms。首对窗口的实际绘制从 24.07 升至 31.73 FPS，模拟从 14.13 升至 16.42 tick/s。活跃合成局的单位数会随战斗减少，其 2D 正式窗口约有 5,900–6,400 单位；判断万兵持续负载应看真实后期局逐秒样本。

最初的后期压力存档从 24,507 个单位开局，交战减员很快。首轮四个窗口中，24,000–26,000 单位的连续开局采样只覆盖 5.06–7.25 秒。预热后的 60 秒实际约有 18,276–20,198 个单位。该轮 2D 为 4.93 → 24.04 FPS、6.69 → 6.19 tick/s，3D 为 8.77 → 31.12 FPS、6.97 → 7.70 tick/s。这四窗作为交战减员对照单独归档。持续约 2.5 万单位的场景改用真实后期局作生成种子，在生成期间加快各地的训练进度，超过 27,000 单位后恢复普通训练，并推进到 25,450 以下，再开始独立的浏览器预热和实测。

修订样本从 tick 22,180 开始，有 25,431 个单位、3,241 支编队。两次独立生成的存档 SHA-256 均为 `a49bc704ffa15868e8277d9f09c52545a6ca541810dbb855dea2db0b153510b2`。用同步引擎逐步核对 2,400 tick，兵力最低 24,965、最高 25,432，最终有 25,346 个单位、3,597 支编队。浏览器中每个正式窗口仍单独检查实际兵力。

首轮四个正式窗口有 25,035–25,213 个单位。2D 的帧率从 26.55 升到 31.93 FPS，模拟从 6.47 升到 8.60 tick/s。3D 的集成版同时可见 459–658 个模型，帧率从 6.05 升到 31.22 FPS，最长帧从 250 降至 94 ms；模拟为 7.26 → 7.06 tick/s。各轮数据和扩展场景回退判定见逐轮对照表。

集成版另优化了国名轮廓和军牌合成。两份存档在 236,709 条边界上的 14 次国名布局与原结果逐项相同，真实后期档首次布局从 1,817 降至 302 ms，一次易主重算从 105 降至 25 ms。活跃玩家的 2D 暂停平移诊断中，显式缓存军牌和战斗标牌的变换图层，将 15 FPS 提升到 25 FPS。

同步和并行引擎在真实存档第 20,700 tick 出现过碰撞差异。每日要塞伤害可能在移动之后、碰撞和占领之前杀死单位。含相应要塞天赋和建筑的结算步现按完整顺序执行。从同一快照推进 1,200 步，其中 1,140 步使用 8 个真实物理 Worker，60 步执行要塞结算，每一步的游戏状态及碰撞报告与同步引擎一致。

在浏览器中，冻结版的 2D 和 3D 固定回放均以 10,907 个单位结束。修正后的两种视角均为 10,908 个。跨版本固定回放对齐了起点、步数和镜头，终态的一兵差异来自并行结算修正。

第一轮集成构建的真实后期 2D 从 22.87 升至 31.90 FPS，最长帧从 218.8 降至 93.6 ms，同时测得 13.77 → 16.60 tick/s。密集 3D 从 9.89 升至 31.97 FPS，最长帧从 219.1 降至 62.8 ms，同时测得 15.08 → 15.63 tick/s。活跃局 2D 从 5.61 升至 26.97 FPS，3D 从 9.19 升至 31.85 FPS。

同一集成构建的固定步数首轮，从 tick 20,638 到 21,838，隔离 Worker、带 2D、带密集 3D 分别耗时 60.72、67.88、72.19 秒，冻结版分别为 61.64、79.47、78.44 秒。旧记录中 2D 为 5.10、3D 为 13.27 tick/s 的差距，在相同模拟区间没有重现。运行画面时的 CPU 竞争仍能影响模拟。集成版 2D 的每步计算均值为 51.74 ms，隔离 Worker 为 38.25 ms；1× 给每步的预算是 50 ms。历史墙钟窗口进入过不同的战局阶段，无法从中单独确定当时差距的成因。

原全图样本开局有 100 个 AI，预热后剩 95 个，正式窗口末尾剩 85 个，该窗口失效。修订样本让每个席位从出生地轮流领取附近地块，各有 6–7 块，并在首都和一个邻区配置普通二级要塞。初始共有 5,200 个合法驻军单位，确定性回放 2,700 步期间每一步均有 100 个存活 AI。鼠标测试选择实际能由 End 键框选进入 3D 的地区，并逐项核对滚轮事件是否送达地图。

在一次完整的桌面输入对照中，两侧六类操作各完成 30 次。滚轮首次反馈 P95 从 405.8 降至 275.5 ms，仍高于 150 ms。集成版从事件时间戳到页面捕获监听器的 P95 为 256.5 ms，从捕获到首个正确画面为 32.1 ms，这两个分位数分别计算。空白页滚轮 P95 约 76 ms。同一集成包的小样本诊断分别试了被动滚轮监听和跳过派遣预览绘制，首次反馈 P95 分别为 268.6、279.8 ms，同组原设置为 282.1 ms。未采用这两项实验改动。触控按地图实际处理的触摸指针移动计时，每次手势先确认手指落到画布，两次反向缩放使用同一对指距。

双端联机首轮出现过服务端步频和指令延迟回退。单独采集服务端 CPU 调用栈时，61 秒内有 70.9% 的采样时长位于引擎步进，20.4% 位于快照广播，其中 JSON 序列化占 15.4%。服务端现在针对相同的客户端基准状态只序列化一份公共世界数据，两端共享这段 UTF-8 字节，各席位的私有天赋选项仍分别编码。保持客户端构建相同，单独更换服务器的一对实测中，步频为 5.90 → 6.37 tick/s，房主和加入者的指令往返 P95 分别为 414 → 307 ms、458 → 401 ms。两个客户端各有 30 次指令获得确认，加入者重新载入后恢复了同一场对局。

生产构建和 635 项核心测试通过。使用同一硬件浏览器验证了 24 项地图、模型和姿态、箭头、军牌、派遣、存档与联机回归。联机用例更新了领土面板所有者的选择器，并单独复跑通过。另用一分钟存档流程核实，定时档保存于 tick 1,460，手动档保存并恢复于 tick 1,462，重载前的 13 个 Worker 全部关闭，恢复后正常派遣成功。30 分钟长局使用独立窗口验收。
