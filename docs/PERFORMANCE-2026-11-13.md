# 帧率实测与优化方案 · 2026-11-13

当前应优先优化地图的 GPU 绘制量，同时单独处理大规模战役的模拟耗时。近景分块裁剪原型在同轮测试中从 **17.0 提升到 32.9 FPS**，没有达到 60 FPS。本次交付基准工具、实测数据和方案；原型通过浏览器拦截模块临时运行，未写入游戏运行代码。

## 测试口径

- Windows、Intel UHD Graphics 630、驱动 31.0.101.2140；Chromium 153，通过 ANGLE D3D11 使用真实 GPU。没有使用浏览器回归测试配置中的 SwiftShader。
- 实测入口为用户正在使用的 Vite 开发服务 `http://127.0.0.1:5187/`；1440×960，设备与渲染像素比均为 1。数据不代表生产包、手机或其他显卡。
- 固定种子 77，主要地图负载为 16 阵营、326 单位；补测 100 阵营、约 1613 单位。均为人工生成的 QA 战役，未宣称是自然游玩到后期的存档。
- 完成 45 个采样窗口，每个 5–7 秒，覆盖静止、连续平移、缩放、运行中的 AI、逐项停用效果和分块原型。窗口串行执行，预先等待地图、贴图与工作线程就绪。
- 平移与缩放通过现有相机语义接口产生连续动作，未包含操作系统输入延迟。帧率以实际 `renderRevision` 增量计数；浏览器 rAF 频率单独记录。
- GPU 耗时使用异步 timer query，分开记录地图主绘制和海岸阴影通道；CPU 耗时不当作 GPU 耗时。绘制统计累计同帧的全部通道，避免 Three.js 默认按 render 调用清零造成漏计。
- 游戏暂停且无变化时，地图停止绘制，浏览器仍约 141 rAF/s。这是已有按需绘制逻辑的正常行为，不能将地图的 0 FPS 作为卡顿结论。

完整测量保存在 [原始结果 JSON](performance/2026-11-13-results.json)。GPU/主线程数据取自浏览器；模拟吞吐数据取自另行运行的 Node 测试。

## 实测结果

16 阵营基线：

| 场景 | 地图 FPS | 绘制间隔 P95 | 每帧 CPU 平均 |
| --- | ---: | ---: | ---: |
| 全球平移 | 12.6 | 118.4 ms | 2.9 ms |
| 全球缩放 | 12.5 | 117.9 ms | 3.0 ms |
| 近景平移 | 15.5 | 124.9 ms | 5.7 ms |
| 近景缩放 | 19.5 | 89.9 ms | 5.4 ms |

低帧率在暂停模拟、视野内几乎没有单位时仍能复现。主线程每帧工作不足以解释全部等待，GPU 查询与隔离实验指向地图几何和海岸通道。

同一轮逐项隔离实验：

| 临时变体 | 全球平移 FPS | 近景平移 FPS | 解释 |
| --- | ---: | ---: | --- |
| 原始效果 | 11.8 | 13.9 | 对照 |
| 关闭海岸阴影 | 17.1 | 24.6 | 当前最大的单项改进 |
| 隐藏陆地网格 | 13.0 | 17.2 | 陆地仍有明显成本 |
| 隐藏边界 | 14.4 | 14.3 | 全球边界有成本，近景仍受海岸限制 |
| 海面改为纯色 | 12.5 | 15.8 | 优先级较低 |
| 隐藏地图文字 | 12.4 | 17.3 | 近景 CPU 从约 5.9 降到 1.4 ms，但 GPU 瓶颈仍在 |
| 渲染像素比降到 0.75 | 15.7 | 16.0 | 降画质收益有限，不作为首选 |

这些停用效果的变体只用于归因，不是拟采用的游戏外观。不同采样窗口存在波动，不能把各项提升直接相加。

## 已验证的优化原型

原型保留所有原始几何、着色器和材质，将海岸、陆地、国界分成空间块，并给每块设置包围体，剔除屏幕外的块。它不改行政区、导航数据或存档。

1. **仅海岸分块，重复两次对照**：近景海岸 GPU 平均耗时从 22.9–24.2 ms 降到 1.6–2.3 ms；近景 FPS 从 16.2–17.3 升到 20.3–20.7。全球海岸通道从约 33 ms 降到 11–12 ms，全球 FPS 从 11.7–13.0 升到 16.0–17.9。
2. **海岸、陆地、国界一起分块，加上平移刷新上限调整**：同轮近景从 18.9 升到 29.8 FPS；每帧三角形从约 189.5 万降到 25.4 万。
3. **独立复测和像素检查**：近景从 17.0 升到 32.9 FPS；海岸 GPU 从 25.2 降到 1.5 ms，主绘制从 21.2 降到 13.1 ms。固定近景相机下比较 1,382,400 像素，最大通道差 1/255，没有像素超过 2/255 阈值。这个检查只覆盖该视角，不能替代日期线、极区、缩放、占领与选择效果的完整视觉回归。

仅把平移上限改为 60，没有明显解决问题：近景仍约 14.8 FPS，GPU 成本没有减少。分块也增加了 CPU 遍历和绘制调用：复测每帧 CPU 从 5.8 增到 7.8 ms。因此正式实现需要控制块数，不能无限细分。

## 大规模战役的第二个瓶颈

100 阵营浏览器实测：暂停时平移约 15.4 FPS；运行时平移约 15.8 FPS，但模拟只有约 **8–10 tick/s**，低于工作线程计划的 20 tick/s。画面刷新和游戏时间推进是两个需要分别解决的问题。

隔离模拟后，预热 10 步，再测 200 步，未开启 CPU profiler 的吞吐结果：

| 阵营 / 单位 | 单步平均 | 单步 P50 | 单步 P95 | 复制状态平均 |
| --- | ---: | ---: | ---: | ---: |
| 3 / 66 | 2.5 ms | 1.9 ms | 5.6 ms | 5.5 ms |
| 16 / 326 | 15.7 ms | 12.1 ms | 25.3 ms | 6.5 ms |
| 100 / 约 1613 | 92.2 ms | 60.6 ms | 374.7 ms | 12.2 ms |

`structuredClone` 是对复制成本的独立估计，不能直接当作浏览器 `postMessage` 端到端耗时。CPU profile 另行录制，热点主要为导航 `plan`、地形查询和单位碰撞。100 阵营采样中 `plan` 自耗时约 5 秒，存在数百毫秒的单步尖峰。

## 实施优先级

**P0：地图分块裁剪与输入刷新调度。**

- 修改 `WorldRenderer.ts`、`coastShadow.ts` 及边界几何管理，采用共享顶点属性/索引和空间块，避免近景仍提交全球陆地、全部海岸和日期线副本。
- 块的包围体必须覆盖屏幕线宽、地形起伏和接缝；国界、归属、占领颜色、选择边框更新需要维护分块索引。保持原有海岸 Max 混合与美术强度。
- 平移与缩放使用一致的活动刷新目标，静止保留按需绘制；调度累计时间，避免高刷新屏上的间隔取整进一步降低实际频率。
- 第一阶段按本机近景稳定 30 FPS 验收，60 FPS 仍是后续目标。不能把本轮原型报告成已稳定 60 FPS。

**P1：远景显示专用 LOD 与文字更新。**

- 全球画面中大部分空间块都可见，分块原型全球仍只有约 16.5 FPS。需增加远景显示网格/边线的简化层级，保持共享边界一致；仅修改渲染资源，继续使用精确原始数据做选择、导航和游戏计算。
- 省名先做空间候选筛选，缓存不变的字体、宽度和属性，减少逐帧重复写入；保持可见文字与相机同步投影，避免拖动时滞后和跳动。
- 分别复测海岸通道、主绘制、文字 CPU 时间。不要用降低全局清晰度替代这一阶段。

**P1：大规模模拟与消息成本，可与渲染工作独立推进。**

- 给导航添加缓存命中、构建次数、单次耗时和内存统计。当前流场缓存仅 4 项；先测按内存预算扩容以及相同目标/速度请求合并的收益，再决定实现。
- 当前已有 AI 决策错峰；进一步处理单次导航构建尖峰，而不是重复增加已有的错峰逻辑。任何分步导航方案需保持命令顺序与可重复性。
- 缓存或复用重复的地形/建筑查询，并验证单位碰撞和通行安全。调整前后比较相同种子的战役结果和单位路径。
- 评估工作线程状态增量、消息合并和 HUD 更新拆分，减少每次复制整份状态。若改变消息协议，应做兼容和回归检查。

**P2：可选画质档。**

在以上优化之后提供低/中/高设置，控制海岸目标分辨率、远景 LOD 和设备像素比；保留高质量默认外观。仅降分辨率、关闭海面或关闭文字的实验没有足够收益，优先级靠后。

## 验收与复测

- 桌面分别验证 1440×960、1920×1080；手机补测真实设备，不能把桌面截图测试当作手机性能证据。
- 每种场景预热后至少采样 15 秒、重复 3 次；同时报告实际绘制 FPS、帧间隔 P95、CPU/GPU 时间、可见/总单位、三角形与模拟 tick/s。
- 视角覆盖全球、近景、日期线和极区；行为覆盖拖动、缩放、占领、选择、新生产单位及大规模调兵。验证轮廓接缝、颜色、阴影和文字方向。
- 生产包另行测量，区分开发模式 React 开销；原型没有完成生产包和全设备验收。

# 使用本机已安装的 Chromium；其他机器按实际安装版本设置。

浏览器探针仅适用于 Vite 开发服务，主动验证被替换的刷新代码；代码结构变化后可能需要同步探针。`--verify` 的像素读回在采样前执行，不计入 FPS。GPU 定时扩展不支持时，数据会缺少 GPU 项，不应推算其数值。
